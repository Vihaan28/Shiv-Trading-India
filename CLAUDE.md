# CLAUDE.md — Project context for Shiv Trading India

Read this first in any session on this repository. It is the working memory for
the project: what it is, how it fits together, the rules that must not be broken,
and what has actually been built so far.

---

## 1. The business

**Shiv Trading India Private Limited** — B2B trading and supply business dealing
in electrical winding and insulation materials.

- Approximately **25 years** in the trade.
- Located at **Bhagirath Palace, Chandni Chowk, New Delhi**.
- Existing site being replaced: `www.shivtradingindia.com`.

**Critical framing rule:** this is a **trading and supply** business, **not a
manufacturer**. Never write copy that describes the company as manufacturing,
producing or fabricating anything. "Supplies", "stocks", "sources", "trades in"
are correct verbs.

**Product range:** 15 categories of winding and insulation material, each
stocked under several brands — see §3b for the full taxonomy and how it maps
to the site's navigation.

### Two goals, in priority order
1. **Serve existing customers** — find a product fast, check availability, add
   several products to one quote request, send it.
2. **Generate new B2B leads** via Google — product and category landing pages,
   clean URLs, real content, clear quote CTAs.

## 2. Hard constraints — do not violate

| Rule | Why |
|---|---|
| Frontend is **HTML5 + CSS3 + vanilla JS only** | No React/Vue/Angular/TypeScript/Tailwind/Bootstrap. Explicit client requirement. |
| **Never invent facts** | No certifications, revenue, employee counts, customer logos, testimonials, review ratings, factories, branch offices, or made-up statistics. If a number is not supplied by the client, do not put it on the site. |
| **Never describe the company as a manufacturer** | See above. |
| Employees have **zero coding knowledge** | Everything they touch must be doable from `/admin` in a browser. No VS Code, no Git, no file uploads, no developer. |
| **One template per dynamic page type** | `product.html` serves every product; `category.html` serves every category. Never generate per-product HTML files by hand. |
| **Unpublished content must never reach the browser** | Filtered out at build time in `scripts/build-content.js`, not hidden with CSS. |

### Placeholders that still need real data
These are live on the site right now and must be replaced before launch:

- **Phone numbers** in `content/settings/contact.md` (`+91 98100 00000`,
  `+91 11 2000 0000`) — invented placeholders.
- **WhatsApp number** — same file, same problem.
- **Email address** — `info@shivtradingindia.com` is a guess.
- **All product imagery** — abstract SVGs generated by
  `scripts/make-placeholders.js`. Real photographs should replace them via the
  CMS media library. (The **logo is real** — see §3a — only the product and
  category artwork is placeholder.)
- **Sample products and categories** — the eleven products in `content/products`
  are realistic but were written by Claude, not supplied by the client. Technical
  specifications in particular need a subject-matter check.
- **Privacy policy** — a plain-language draft. Needs legal review against the
  Digital Personal Data Protection Act, 2023.

No product has a numeric price set; everything is `price-on-request`, which is
both realistic for metals (prices track the market daily) and avoids publishing
invented figures.

## 3. Architecture

```
Employee edits at /admin (Decap CMS)
        │
        ▼
Decap commits Markdown to  content/{products,categories,settings}/*.md
        │
        ▼
Netlify detects the commit and runs:  npm run build
        │
        ▼
scripts/build-content.js  →  /data.json   (published content only)
                          →  /sitemap.xml (all public URLs)
        │
        ▼
Browser loads a static HTML page, fetches /data.json once,
vanilla JS renders products / categories / search / cart
```

**Why a build step:** Decap writes Markdown with YAML front matter, which
browsers cannot read. The build flattens it into one JSON file the frontend
fetches with a single request. It also filters drafts, validates fields, and
warns about broken category references without ever failing the deploy.

### Content pipeline rules
- `scripts/build-content.js` is the **only** thing that writes `data.json` and
  `sitemap.xml`. Both are committed to Git deliberately (so the site works
  without a build) but are regenerated on every deploy.
- The build **never throws** on one bad content file — it warns and skips.
  A single malformed product must not take the website offline.
- If you add a CMS field in `admin/config.yml`, you **must** also read it in
  `build-content.js`, or it will be silently dropped.
- The build accepts both flat fields and the older nested `pricing:` / `seo:`
  shapes, so content written under an earlier config keeps working.

### 3a. Brand assets

`assets/images/logo.png` is the **client-supplied source artwork** — the "STi /
Powering Performance" lockup, black and orange on a white background,
1654 × 951. Never edit or delete it; it is the master.

`scripts/process-logo.js` (`npm run logo`) derives the web variants from it:

| File | What it is | Used by |
|---|---|---|
| `logo-mark.png` | The STi wordmark + arc, tagline removed, whitespace trimmed, white keyed to transparent, 212 × 84 | Header, apple-touch-icon, Organization JSON-LD, CMS login screen |
| `logo-mark-light.png` | Same, with the black ink recoloured to near-white; the orange is preserved | Footer (dark background) |
| `logo-full.png` | The complete lockup including the tagline, 434 × 220 | Not currently used — available for social cards and print |

Implementation notes worth knowing before touching that script:

- Transparency is recovered by **un-premultiplying** against white
  (`a = 1 − min(R,G,B)/255`), not by keying out white pixels. A plain key
  leaves a hard halo on the anti-aliased letterforms.
- Downscaling is a box filter **in premultiplied alpha**. Averaging straight
  RGBA drags the arbitrary colour of transparent pixels into the edges.
- The light variant separates orange from black using **absolute chroma plus a
  brightness floor**, not relative saturation. This matters: a near-black pixel
  of `(0, 4, 9)` in the glossy lettering scores a relative saturation of 1.0 and
  would be mistaken for brand colour. That was a real bug during the build.
- Output is capped at 84px tall. The artwork has glossy gradients that PNG
  compresses poorly — at full size the header logo was 621 KB.

**The site palette was deliberately not changed to match the logo's orange.**
The copper accent (`--copper: #a9632c`) stays as the UI colour; the orange reads
as a brand mark. This was an explicit decision, not an oversight.

`favicon.svg` is hand-written to echo the mark (italic "STi", orange `i`, on the
ink background). `make-placeholders.js` no longer generates any logo or favicon —
those are real assets now.

### URLs
Netlify rewrites (status 200, so the address bar keeps the pretty URL):

```
/product/<slug>   →  product.html
/category/<slug>  →  category.html
```

`STI.ui.readSlug()` reads the slug from the path, falling back to `?slug=`.
These pretty URLs are what goes in `sitemap.xml` and in each page's canonical
tag. There is deliberately **no catch-all redirect** — Netlify serves `404.html`
for anything unmatched, which is correct for a multi-page site.

**Local dev needs the same rewrites.** `netlify.toml` only applies once
deployed to Netlify — a plain static server has no idea `/category/<slug>`
should serve `category.html`, and will 404 on every category/product link.
`serve.json` in the project root mirrors the same two rewrites for `npx serve`
(what `npm run dev`/`npm run serve` use). If the dev command ever changes away
from `serve`, carry this rewrite pair over to whatever replaces it.

### Forms
Both forms are **Netlify Forms**. The static markup in `rfq.html` and
`contact.html` is what registers them at deploy time — if you remove a field
from the HTML, Netlify stops accepting it.

Submission goes through `fetch` (`STI.submitNetlifyForm`) rather than a native
POST, so the page can validate first and keep the cart until the send succeeds.
Both forms have a honeypot field (`company-website`) for spam.

**Enquiries are read at:** Netlify dashboard → the site → **Forms** → `rfq` or
`contact`. Email notifications must be configured there; they are not on by
default.

### 3b. Catalogue taxonomy: Category → Brand → Product

The site navigates in three steps, not two:

```
products.html          category.html                product.html
"15 categories"    →   "brands within one       →   one brand's full
 (category cards)        category" (brand cards)       product page
```

This is **not** a new content type. "Brand" is not a CMS collection — a brand
is just a normal product entry whose **name already includes the brand**
(`"BIC Enamelled Copper Winding Wire"`), plus an optional `brand` field used
only for display (a labelled "Brand: BIC" line on the product page). Two
collections, same as before: **categories** and **products**. The three-page
navigation falls out of how those two collections are rendered:

- **`products.html`** — renders every category as a card (`main.js`,
  `renderProductsIndex()`), sorted by each category's **Display Order** field.
  It used to be a filterable all-products catalogue; that mode was removed
  entirely when this taxonomy was introduced (see the work log). There is no
  "browse everything unfiltered" page anymore — `search.html` is the only place
  that spans categories.
- **`category.html`** — unchanged in spirit from before, but now conceptually
  "choose a brand": it lists the products (`STI.productsIn(categorySlug)`)
  belonging to one category, with search/sort/availability filtering. A
  category with only one product (see below) still renders this page — it just
  shows a single card. That is a deliberate, confirmed decision: category cards
  behave identically whether or not the category has multiple brands, rather
  than special-casing single-product categories to skip straight to
  `product.html`.
- **`product.html`** — unchanged. One brand's product detail.

**The 15 categories, in the exact order the client specified** (this is the
`displayOrder` in each category's front matter — **never re-sort these
alphabetically**; getting this wrong once already broke the client's expected
ordering when the old all-products page interleaved brands from different
categories):

1. Enamelled Copper Winding Wire — BIC, Devidayal, Essell, RR Shramik, HWP, Highseas
2. Submersible Copper Wire — Essell, PolyHWP, Swastik, Premier
3. Enamelled Aluminium Winding Wire — BMI, Polywin
4. Submersible Aluminium Wire — HWP
5. F-Class Insulation Paper — Thermoflex, Unprinted
6. Polyester Film (Electrical Grade) — Garware, JBF
7. Kraft Paper (Electrical Grade) — ASPHA (Black, Undyed), Imported
8. Insulating Varnish — Jyoti, Dr. BECK
9. B-Class Insulating Paper — *no brand* (one product, same name as category)
10. Fiber Glass Wire — HWP
11. Insulating Sleeves — Premier (F-Class), Silicon, China, Heat Shrink
12. Insulating Tapes & Threads — Cotton, Adhesive, Thread (no brand on any)
13. DCC / DPC Copper & Aluminium Wires — 4 standalone products, no brand
14. Bare Copper Winding Wire — *no brand*
15. Copper Strips — *no brand*

37 products total. Naming conventions used when authoring these:

- **Simple brand + category** (categories 1–6, 8, 10): `"{Brand} {Category
  Name}"`, e.g. `"Garware Polyester Film (Electrical Grade)"`.
- **Nested variant** (category 7, Kraft Paper): brand `ASPHA` splits into two
  separate product entries — `"ASPHA Kraft Paper – Black"` and `"ASPHA Kraft
  Paper – Undyed"` — rather than modelling a fourth content level. `"Imported
  Kraft Paper"` is the third product in that category.
- **Standalone descriptive name, no brand suffix** (categories 11–13): the
  product name *is* the distinguishing label already
  (`"Silicon Insulating Sleeve"`, `"DCC Copper Wire"`) — these do not get a
  category name appended.
- **Solo, no-brand categories** (9, 14, 15): exactly one product, named
  identically to the category.

**Content is intentionally thin right now.** Every scaffolded product has
`priceType: price-on-request`, `availability: on-request`, and an **empty
`specifications` array** — no invented technical numbers attached to a real
brand name. The client's own instruction on this: *"just add the products with
brand names, when the admin portal is finalised, I will have you give a
provision there for having access to edit all this data by an employee."* The
CMS (`admin/config.yml`) already exposes every field an employee would need
(specifications, brand, pricing, availability, images) — nothing further is
required to make this editable; the content just hasn't been filled in yet.

**Product images are shared per category, not per brand.** There is no way to
visually distinguish two brands of the same raw material without real
photography, so every product's `primaryImage` points at its own category's
placeholder (`/assets/images/placeholders/cat-<category-slug>.svg`). This
halves the image-generation work and is more honest than fabricating distinct
imagery per brand. `scripts/make-placeholders.js` has a `CATEGORY_IMAGES` table
that must stay in sync with the categories in `content/categories/` — if a
category is renamed or added, update both the content and that table (and
re-run `npm run placeholders`).

**Homepage curation:** exactly 6 categories are marked `featured: true`
(Enamelled Copper Winding Wire, Enamelled Aluminium Winding Wire, F-Class
Insulation Paper, Polyester Film, Kraft Paper, Insulating Sleeves), and one
product per featured category is marked `featured: true` /
`showOnHomepage: true` (the first brand listed in that category). This is an
editorial choice, not a rule — an employee can change which categories/products
are featured at any time through the CMS.

**`priceUnit` gained `per litre`** (for Insulating Varnish) — see the
`priceUnit` options list in `admin/config.yml` and `UI.UNITS` /
`UNIT_FROM_PRICE` in `assets/js/ui.js`.

## 4. Code map

```
/                       index, about, products, product, category, rfq,
                        contact, search, privacy-policy, thank-you, 404
/admin/                 Decap CMS (index.html + config.yml)
/content/               CMS-managed Markdown — the source of truth
/assets/css/            variables → main → components → pages → responsive
                        (load order matters; responsive.css must be last)
/assets/js/             see below
/assets/images/         logo, favicon, generated placeholders, uploads/
/scripts/               build-content.js (build), make-placeholders.js (dev)
data.json, sitemap.xml  GENERATED — do not hand-edit
```

### JavaScript modules

Everything hangs off one global, `window.STI`. No bundler, no modules — plain
scripts loaded in a fixed order. Every page module starts with
`STI.load().then(...)`, which resolves once `data.json` has been fetched (and
never rejects — it falls back to empty data and logs).

| File | Responsibility |
|---|---|
| `data-loader.js` | Fetches `data.json`. All read helpers: `products()`, `categoryBySlug()`, `setting()`, `searchProducts()` |
| `ui.js` | **All shared rendering.** `esc()`, `productCard()`, `categoryCard()`, `priceHtml()`, `availabilityBadge()`, `toast()`, `markdown()`, `jsonLd()` |
| `navigation.js` | Sticky header, mobile drawer, search panel, CMS-driven contact details + footer categories |
| `animations.js` | IntersectionObserver scroll reveals, hero parallax |
| `rfq.js` | Cart (localStorage), RFQ page, Netlify form submission, validation |
| `catalog.js` | category.html only — the always-locked-to-one-category "choose a brand" grid (search/sort/availability). Does **not** run on products.html; see §3b. |
| `product.js` | Product detail template, gallery, related, Product JSON-LD |
| `search.js` | Search page + header search form |
| `main.js` | Homepage / **products-index** / about / contact controllers, Organization JSON-LD |

**Load order on every page:** `data-loader → ui → navigation → animations →
rfq → search → [page module] → main`.

### Rules for touching the JS
- **Never build a product card outside `ui.js`.** The first draft of this
  project duplicated card markup across three files and they drifted. One
  function, used everywhere.
- **Always escape CMS content** with `UI.esc()` before it goes into
  `innerHTML`. Product names come from user input.
- Cart stores **only** `{slug, quantity, unit}`. Names, images and prices are
  looked up fresh from `data.json` on every render, so nothing goes stale when
  a product is edited. `Cart.prune()` drops entries whose product disappeared.
- Anything that changes the cart must keep `#rfqProducts` in sync — that hidden
  textarea is what Netlify actually receives. This is wired through the
  `sti:cart-changed` event.
- New cards injected into the DOM need `STI.reveal(container)` or they stay at
  `opacity: 0`.

### Rules for touching the CSS
- Tokens live in `variables.css`. Do not hardcode colours or spacing elsewhere.
- Radii and shadows are deliberately small. The design reads premium through
  spacing, type and hairlines — not rounded boxes and drop shadows.
- Copper is an **accent**, never the dominant colour.
- Everything animated must be inert under `prefers-reduced-motion: reduce`.
- `/assets/css/*` and `/assets/js/*` are served `must-revalidate` because the
  filenames are not content-hashed. Do not "optimise" that to a long cache.

### Session 3 — Category → Brand → Product restructure (Claude, same day)

The client's original 11-product, 7-category sample catalogue was replaced
entirely with a real 15-category, 37-product taxonomy the client dictated, and
the site's navigation was changed from a two-level (category → product) to a
three-level (category → brand → product) flow. Full details in §3b — summary
of what changed and why:

- **`products.html` rewritten.** It was a filterable all-products catalogue
  with a category sidebar; it is now a static-in-spirit grid of all 15
  category cards (`main.js`, new `renderProductsIndex()`), in Display Order.
  `catalog.js` no longer loads on this page at all.
- **`catalog.js` simplified.** Removed the entire "no category locked, show
  everything with a category filter" branch — `categorySlug` now always comes
  from the URL, since category.html is its only remaining caller. This deleted
  `buildCategoryFilter()` and the `#filterCategories` handling outright, not
  just stopped calling them, since they had become genuinely dead code.
- **Content fully replaced.** All prior categories/products deleted; scaffolded
  the new taxonomy via a one-off Node script (not kept in the repo) from a data
  table matching the client's exact list and order.
- **Added a `brand` field** to the product schema end-to-end: CMS
  (`admin/config.yml`), the build script (`scripts/build-content.js`), and
  display (a "Brand: X" line on the product page only — deliberately **not**
  repeated on the card, since the product name already contains the brand
  there and a second mention read as redundant clutter).
- **Added `per litre`** as a price unit (Insulating Varnish is sold by volume).
- **Placeholder images consolidated to one per category** rather than one per
  product — see §3b for why. `make-placeholders.js` rewritten around a
  `CATEGORY_IMAGES` table; two new tones added (`varnish`, `glass`).
- **`serve.json` added.** The client hit a live bug: clicking a category card
  during local testing produced a bare "cannot GET" error. Root cause —
  `netlify.toml`'s `/category/<slug> → category.html` rewrite only applies once
  deployed to Netlify; `npx serve` (used by `npm run dev`/`npm run serve`) knew
  nothing about it and 404'd on every clean URL. `serve.json` mirrors the same
  two rewrites for local serving. **If the dev server tooling ever changes,
  carry this forward or local testing of any product/category link breaks
  again.**
- **A related but distinct complaint** — "categories aren't in the order I
  specified" — turned out to be a symptom of the *same* underlying page (the
  old flat products.html catalogue interleaved brands from different
  categories because it sorted all 37 products together by a per-category
  `displayOrder` that resets to 1 in every category). The category-level
  `displayOrder` in `data.json` was already correct throughout; replacing that
  page was the actual fix, not a sort-order bug.

Client decisions on record from this session:
- Categories with no brand list still render `category.html` (showing one
  product card) rather than skipping straight to `product.html`. Every
  category card behaves identically regardless of how many products it holds.
- No fabricated technical specifications against real brand names. Every
  scaffolded product ships with `specifications: []`; the client will have
  employees fill these in through the CMS once it's finalised.

### Session 4 — Netlify Identity invite flow fixed (Claude, same day)

Client reported: added their email under Netlify Identity → Invite users,
received the invite email, clicked it, and it "redirected to the public
website" with no way to actually log in to `/admin`.

**Root cause:** Netlify Identity invite/recovery/confirmation links point at
the site's homepage with an auth token in the URL hash (e.g.
`yoursite.com/#invite_token=...`), not at `/admin/`. Only `admin/index.html`
had the Netlify Identity widget script loaded — the public homepage had no
code that could notice or act on that token, so it was silently dropped and
the visitor just saw the ordinary site.

**Fix:** added the same Netlify Identity widget + an `on('login')` redirect to
`/admin/` at the bottom of `index.html` (see the comment there). The widget
auto-detects a token in the URL wherever it's loaded and shows the
set-password screen; the redirect then sends a newly-confirmed user straight
into the CMS instead of leaving them on the homepage.

**Important:** this only works once the site has been **redeployed** with this
change. The original invite token is not consumed by loading a page that
ignores it, so the client should click the *same* link from the original
invite email again after the next deploy, rather than needing a fresh invite.
Documented in `ADMIN-GUIDE.md` under "Inviting an employee".

If invites are still silently swallowed after this, the next thing to check is
whether Identity's configured **Site URL** (Netlify → Site configuration →
Identity → Settings) actually matches where the site is really deployed —
a mismatch there sends the token to a URL this fix was never loaded on.

### Session 5 — Sitewide CMS text editability (Claude, same day)

Client asked for full CMS control over "all headings, subheadings, texts,
options, general details" on every page. Scoped and built as follows.

**Scope decision (stated plainly, not asked as a blocking question):** made
editable every heading, subheading, paragraph and button label a visitor
reads, across all 10 pages, plus shared site-wide chrome (nav labels, footer
headings, repeated buttons like "Add to quote"). **Deliberately left fixed:**
`aria-label`/screen-reader-only text, form validation error messages, and
generic filter-panel chrome ("Filter", "Reset", "Sort", "Featured first" /
"Name A-Z" sort options). These carry accessibility/functional risk if
mistyped and zero business value if reworded — leaving them fixed is a
considered choice, not an oversight, and is worth revisiting only if asked.

**No new CMS collection was needed.** `buildSettings()` in
`scripts/build-content.js` already passes through *any* key found in a
`content/settings/*.md` file verbatim — it was written generically from the

**Field naming gotcha, now fixed, worth remembering:** `buildSettings()` keys
`data.json.settings` by **filename minus extension**, not by the CMS's
internal `name:` field. The settings files must be named to exactly match
what the JS calls `STI.settingGroup('...')` with — `productsPage.md`, not
`products-page.md`. Got this wrong on the first pass (used hyphenated
filenames with camelCase JS lookups), which silently no-op'd every field in
those three files. If you add a new settings file, **the filename IS the key**
— camelCase both, keep them identical, and verify with
`node -e "console.log(require('./data.json').settings.yourKey)"` before
assuming a field works.

**`404.html` and `thank-you.html` didn't load `main.js` at all** before this
session (they were originally static-only pages). Discovered when their new
CMS text silently failed to paint with zero console errors — the giveaway that
it's a missing script tag, not a broken settings key, is when a field
resolves correctly in `data.json` but the page never even tries to use it.
Both now load the full script stack and have a `renderUtilityPage()`
controller in `main.js`.

**One correctness fix distinct from the CMS work:** `products.html` had a
hardcoded `"15 categories"` eyebrow. Left as static text, it would silently go
stale the next time a category is added or removed. Changed to a computed
`${categories.length} categories` in `renderProductsIndex()` instead of a CMS
field — this one should never be editable text, because it isn't actually
text, it's a fact about the data.

**`contactFormIntro` needed an inline link inside otherwise-plain CMS text**
("Use the quote request instead", where "quote request" links to `/rfq.html`).
Solved by authoring it as `[quote request](/rfq.html)` and adding
`UI.inlineText()` to `ui.js` — applies the same inline `[text](url)`/`**bold**`
substitutions as `UI.markdown()` but without the block-level `<p>` wrapper
`UI.markdown()` always emits, which would have nested invalidly inside the
existing `<p id="ctFormIntro">`.

**Icon-only cart button removed from the nav** (separate client request,
same session): the header previously had both an icon-only cart-count badge
*and* a "Request a quote" text button, both linking to `/rfq.html` — genuinely
redundant. Removed the icon button; the text button's existing
`(N)` count suffix (via `[data-cart-label]` in `rfq.js`) already conveyed the
same information. The bump animation that used to pulse the icon badge on
add-to-cart now pulses the `.nav-cta` button itself instead

feedback isn't lost.
